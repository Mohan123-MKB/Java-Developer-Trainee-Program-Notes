**1. What is the current problem?**

* In **our** Payment Validation Service, we currently verify the HMAC signature inside PaymentServiceImpl for POST /v1/payments.
* Our **aim** is to authenticate every incoming request before it reaches the controller and before any further payment processing happens.
* In the **future**, we might add more endpoints:

&#x09;- POST /v1/payments

&#x09;- GET /v1/payments/{id}

&#x09;- POST /v1/refunds

If we manually add security checks to every endpoint, a developer might forget one, creating a security risk.

* **Solution**: We need centralized security that validates requests before they reach the controllers.



===========================================================================================================================================================================================



**2. How does Spring Security solve this?**

Spring Security provides a centralized way to protect our APIs, reducing the risk of forgetting security checks when new endpoints are added.



**Flow:**

Client → Tomcat Web Server → Spring Security Filter (checks configured security rules and HMAC signature) → Valid request continues / Invalid request is rejected → Dispatcher Servlet → Controller → Service → Database



===========================================================================================================================================================================================



**3. Why need spring security:Key benefits**

Centralized security: Manage security logic in one place.

Authentication: Verify who is making the request.

Authorization: Control which resources or actions an authenticated user can access.

Safer future endpoints: Reduce the risk of missing security checks when adding new APIs.

Extensibility: Add other security mechanisms in the future. (JWT, OAUTH2.0)



===========================================================================================================================================================================================



**4. How spring security actually works?**

1. Client (Postman) → Sends an HTTP request.
2. Tomcat Server → Receives the request.
3. DelegatingFilterProxy → Connects Tomcat's filter mechanism to Spring Security.
4. FilterChainProxy → Selects the appropriate SecurityFilterChain.
5. Security Filters → Check authentication, authorization, CSRF, HMAC, and other configured security rules.
6. DispatcherServlet → Routes the request to the controller.
7. Controller → Service → Database → Processes the request.
8. HTTP Response → Returns the response to the client.



===========================================================================================================================================================================================

**6. How does Spring Security use filters?**

1. DelegatingFilterProxy: Connects the servlet container's filter mechanism to Spring-managed security infrastructure.
2. FilterChainProxy: Selects the appropriate Spring Security filter chain for an incoming request.
3. SecurityFilterChain: Defines the security filters and rules for matching requests.
4. Security filters: Perform checks such as authentication, authorization, and CSRF protection. We can also add our custom HMAC verification filter.



**Note:**

We generally configure Spring Security using Spring configuration rather than manually calling every security filter.

Filter: Processes a request before it reaches the controller.

Filter chain: A sequence of filters that execute in order.

Spring Security: Uses filters to enforce security rules centrally.



===========================================================================================================================================================================================



**How do Spring Security filters work?**

\- Spring Security provides built-in security filters to process incoming HTTP requests.

\- When we send a request from Postman, it passes through a chain of security filters before reaching the controller.

\- FilterChainProxy manages the security filter chain.

\- We can enable TRACE logging to see which filters execute and what happens internally.

&#x20;                Add this to application.properties:

&#x20;         logging.level.org.springframework.security=TRACE



**Why did our POST request fail?**

\- The CsrfFilter checks whether the request contains a valid CSRF token.

\- Our POST request did not contain a valid token, so the filter rejected the request before it reached the controller.



**What is CSRF?**

\- CSRF (Cross-Site Request Forgery) is a browser-based attack.

\- An attacker tricks a user's browser into sending an unwanted request to a website where the user is already logged in.

\- The browser may automatically attach session cookies, making the request appear authenticated.

\- CSRF protection helps prevent such unauthorized requests.



**Why can we disable CSRF for our REST API? (API is Stateless so mostly we don't use CSRF)**

\- Our REST API is designed to be stateless, meaning the server does not rely on a session to maintain authentication between requests.

\- We use HMAC-SHA256 to authenticate each request independently.

\- The merchant backend sends an HMAC signature with every request, and our server verifies it.

\- Since authentication does not rely on browser cookies or sessions, CSRF protection can generally be disabled for this API.

**Stateless Behaviour in Spring Security:**

\- Configure Spring Security with STATELESS so every request is authenticated independently.

\- With stateful session behaviour, the server may reuse authentication through the JSESSIONID cookie, even when Basic Auth credentials are not sent again.

\- With stateless behaviour, the server does not use an HTTP session to remember authentication between requests.

\- Therefore, every request must include its own credentials, such as Basic Auth or a valid HMAC signature.



**1. .anyRequest().authenticated()**

\- AuthorizationFilter checks whether the user is authenticated using SecurityContextHolder.

\- If authenticated, the request continues to the controller.

\- If not authenticated, the request is rejected.

\- BasicAuthenticationFilter validates the username and password and stores the authenticated user in SecurityContextHolder.

**2. Other authorization options**

\- .anyRequest().authenticated() — Requires authentication.

\- .anyRequest().permitAll() — Allows all requests.

\- .anyRequest().denyAll() — Rejects all requests.

\- Role-based: Allows access based on roles like ADMIN or USER.

\- Path-based: Applies different rules to different API endpoints.

**3. Stateless Behaviour**

Stateless means the server does not store authentication in a session for reuse across requests.

\- Every request must provide its own credentials.

\- HTTP Basic requires credentials with every request.

\- Our HMAC API requires a valid signature with every request.

.sessionManagement(session ->

&#x20;   session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))

**How do you control your request in security filter chain before reached to controller? :**



**1. Closing the gate before the controller**

Spring Security checks incoming requests before they reach the controller. We verify the request's authentication and authorization. Only valid, authorized requests are allowed to continue to payment processing.



**2. What does the last filter do?**

AuthorizationFilter is typically the last filter in Spring Security's default filter chain. It checks whether the request is allowed based on the configured authorization rules.



**3. How does .anyRequest().authenticated() work?**

\- Spring Security checks whether the request has an authenticated user in the SecurityContextHolder.

\- If an authenticated user is available, the request can continue, provided the authorization rules allow it.

\- If the user is not authenticated, Spring Security rejects the request or initiates an authentication response.



**4. What does the Basic Authentication filter do?**

\- The BasicAuthenticationFilter checks the username and password provided in the HTTP Basic Authorization header.

\- If the credentials are valid, it creates an authenticated Authentication object and stores it in the SecurityContextHolder.

\- Later, AuthorizationFilter checks the authentication against the configured authorization rules.



**5. In our HMAC project**

We will implement a custom HMAC filter to verify the incoming signature. If verification succeeds, the filter establishes authentication in the SecurityContextHolder. The authorization rules then determine whether the request can proceed to the controller.



Flow:

Client → Security Filters → HMAC Authentication → SecurityContextHolder → AuthorizationFilter → Controller → Payment Processing
