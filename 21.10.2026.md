Why use nested classes?

Instead of declaring all fields directly inside one class, we group related data into separate classes.

\- PaymentReq holds the complete payment request.

\- User contains customer information.

\- Payment contains payment information.

\- LineItem contains information about each product.

This structure improves code organization, readability, and maintainability.

The fields user and payment are reference variables that hold references to objects of their respective classes.



&#x09;**5. Creating the Request Using Java Objects**

Suppose a client wants to send a payment request containing customer information and one product.



The request can be created in Java as follows:

PaymentReq request = new PaymentReq();



// Create the user object

PaymentReq.User user = new PaymentReq.User();



user.setEndUserId("USER101");

user.setFirstName("Ravi");

user.setLastName("Kumar");

user.setEmail("ravi@example.com");

user.setCountry("IN");



// Create the line item

PaymentReq.LineItem item = new PaymentReq.LineItem();



item.setProductName("Laptop");

item.setQuantity(1);

item.setCurrency("INR");

item.setUnitAmount(50000);



// Create the payment object

PaymentReq.Payment payment = new PaymentReq.Payment();



payment.setTotalAmount(50000);

payment.setCurrency("INR");

payment.setPaymentType("SALE");

payment.setPaymentMethod("APM");

payment.setProvider("STRIPE");



payment.setLineItems(List.of(item));



// Attach user and payment to the main request

request.setUser(user);

request.setPayment(payment);

Here, the PaymentReq object contains references to the User and Payment objects. The Payment object contains a list of LineItem objects.



This creates the complete request structure in memory.

**=> How HmacSHA256 ensured authentication and data integrity:**



\- For the same message and secret key, the same HMAC signature is generated.

\- If the message or secret key changes, the signature will be different.

\- Authentication: A valid signature helps confirm that the sender knows the correct secret key.

\- Data Integrity: Matching signatures confirm that the received message has not been changed.

\- It is extremely difficult to create a valid signature without knowing the secret key.

\- We cannot recover the original message or secret key from the HMAC signature.

\- HTTPS protects data during transmission, but if an attacker compromises the merchant or PIS system, the secret key may be exposed. Therefore, we must protect the secret key securely.

**# 🚀 Day 9 – HMAC-SHA256: Authentication and Data Integrity**



**Today, I learned how \*\*HMAC-SHA256\*\* helps secure APIs by verifying the sender's authenticity and detecting data tampering.**



**### 1. Why Do We Need Security?**



**- \*\*Authentication:\*\* Verifies the identity of the sender.**

**- \*\*Authorization:\*\* Checks whether the sender has permission to perform an operation.**

**- \*\*Data Integrity:\*\* Ensures that data has not been modified during transmission.**

**- \*\*Production Security:\*\* Helps protect applications against unauthorized access and cyberattacks.**



**### 2. What Is HMAC-SHA256?**



**- \*\*HMAC\*\* – Hash-Based Message Authentication Code.**

**- \*\*SHA-256\*\* – A cryptographic hash function.**

**- HMAC-SHA256 uses a secret key and message data to generate a signature, commonly encoded in Base64 or hexadecimal format.**

**- It helps verify \*\*authentication and data integrity\*\* when implemented correctly.**



**### 3. HMAC-SHA256 Workflow in Payment Validation Service**



**1. The payment integration system generates a unique secret key for each merchant.**

**2. The secret key is securely shared with the authorized merchant.**

**3. The merchant prepares the JSON request body.**

**4. The merchant generates an HMAC-SHA256 signature using the request data and secret key.**

**5. The merchant sends the API request with the JSON body and signature in an HTTP header.**

**6. The Validation Service receives the request and extracts the signature from the header.**

**7. The service generates a new signature using the received request data and the stored merchant secret key.**

**8. The service compares the generated signature with the incoming signature.**

**9. If they match, the signature is valid and the signed data has not been altered, assuming the same canonicalization rules are used.**

**10. If they do not match, the service rejects the request.**



**### 4. How Does It Ensure Security?**



**- \*\*Authentication:\*\* A valid signature demonstrates that the request was created by someone with access to the shared secret key.**

**- \*\*Data Integrity:\*\* If the signed data changes, the calculated signature will generally change, causing verification to fail.**



**### 5. End-to-End Diagram**



**Merchant prepares JSON request → Generates HMAC-SHA256 signature → Sends request body + signature header → Validation Service recalculates signature → Compares signatures → Accepts or rejects request.**
