###### **2. Five approaches to business validation:**



**Approach 1: One method**

Put all validation logic into one method.

**Problem:** The method becomes large and difficult to maintain.



**Approach 2: Separate methods**

Create one method for each validation check in the same class.

**Problem:** The service class can still become too large.



**Approach 3: Separate classes**

Create a separate Java class for each validation rule and register it as a Spring bean.

**Benefit:** Each rule is easier to maintain. However, many classes may be created.



**Approach 4: Common interface**

Create a BusinessValidator interface that every validator implements.

**Benefit:** All validators follow the same contract. This is the foundation of the Strategy Design Pattern.

**All validators follow the same contract/Interface means:** Here validators are classes, if subclasses wants to perform the same behaviour in different ways then we use Interface. (common contract, all subclasses implements this interface(contract) and provide different implementations.

**1. Real-world example: A hospital**

Imagine a hospital has three different departments:

\- Cardiology

\- Neurology

\- Orthopedics

Every department must provide a method called treatPatient(), but each department treats patients differently.



**For example:**

\- Cardiology treats heart problems.

\- Neurology treats brain and nerve problems.

\- Orthopedics treats bone problems.



**We can define a common contract using an interface. (also like payment -> UPI, CARD, PAYPAL)**

interface HospitalDepartment {

&#x20;   void treatPatient();

}



**Each department implements that interface:**

class Cardiology implements HospitalDepartment {

&#x20;   public void treatPatient() {

&#x20;       System.out.println("Treating heart problems");

&#x20;   }

}



class Neurology implements HospitalDepartment {

&#x20;   public void treatPatient() {

&#x20;       System.out.println("Treating brain problems");

&#x20;   }

}



class Orthopedics implements HospitalDepartment {

&#x20;   public void treatPatient() {

&#x20;       System.out.println("Treating bone problems");

&#x20;   }

}



**What is the benefit?**

Every department follows the same contract: treatPatient().

But each department has its own implementation.

The hospital doesn't need to use a different method name for every department.

**2. Now apply the same idea to your Payment Validation Service**

Suppose your payment service has three business validation rules:

\- AmountValidator — checks whether the payment amount is valid.

\- CurrencyValidator — checks whether the currency is supported.

\- MerchantValidator — checks whether the merchant is allowed.



Without a common interface, different developers might write different method names:

amountValidator.checkAmount(req);

currencyValidator.validateCurrency(req);

merchantValidator.checkMerchant(req);

The service needs to know the method name for every validator.



**We can solve this problem with a common interface.**

**Step 1: Create BusinessValidator**

public interface BusinessValidator {

&#x20;   void validate(PaymentReq req);

}

This means every business validator must provide a method named validate() that accepts a PaymentReq.



**Step 2: Implement the interface**

AmountValidator.java

@Component

public class AmountValidator implements BusinessValidator {



&#x20;   @Override

&#x20;   public void validate(PaymentReq req) {

&#x20;       if (req.getPayment().getTotalAmount() <= 0) {

&#x20;           throw new IllegalArgumentException(

&#x20;               "Payment amount must be greater than zero"

&#x20;           );

&#x20;       }

&#x20;   }

}



CurrencyValidator.java

@Component

public class CurrencyValidator implements BusinessValidator {



&#x20;   @Override

&#x20;   public void validate(PaymentReq req) {

&#x20;       String currency = req.getPayment().getCurrency();



&#x20;       if (currency == null || currency.isBlank()) {

&#x20;           throw new IllegalArgumentException(

&#x20;               "Currency is required"

&#x20;           );

&#x20;       }

&#x20;   }

}



Now both validators have the same method:

validate(PaymentReq req)



**However, their internal validation logic is different.**

**Step 3: Call both validators in the same way**

List<BusinessValidator> validators = List.of(

&#x20;   amountValidator,

&#x20;   currencyValidator

);



for (BusinessValidator validator : validators) {

&#x20;   validator.validate(paymentReq);

}

The service doesn't need to know whether it is calling AmountValidator or CurrencyValidator. It calls validate() on both.

If the amount is invalid, the exception stops the loop, so the currency check won't run.



**Approach 5: Dynamic configuration:**

Store validator names in application.properties so we can configure which rules execute and in what order.

**Benefit**: We can change the configured rule list without changing the Java execution logic. Live changes require additional configuration-reloading support.

###### **3. Strategy Design Pattern:**



Definition: The Strategy Pattern allows different algorithms to be implemented separately and used through a common interface.

In our project:

\- Interface: BusinessValidator

\- Strategies: ValidatorCheck1, ValidatorCheck2

\- Invoker: PaymentServiceImpl



**Step 1: Create the interface**

public interface BusinessValidator {

&#x20;   void validate(PaymentReq req);

}

Every validator must implement the validate() method.



**Step 2: Create validator classes**

@Component

public class ValidatorCheck1 implements BusinessValidator {



&#x20;   @Override

&#x20;   public void validate(PaymentReq req) {

&#x20;       System.out.println("ValidatorCheck1 executed");

&#x20;   }

}



@Component

public class ValidatorCheck2 implements BusinessValidator {



&#x20;   @Override

&#x20;   public void validate(PaymentReq req) {

&#x20;       System.out.println("ValidatorCheck2 executed");

&#x20;   }

}



**Step 3: Configure the rules**

In application.properties:

validator-rules=VALIDATOR\_CHECK1,VALIDATOR\_CHECK2

This specifies which validators should execute and their order.



**Step 4: Map names to classes**

private final Map<String, Class<? extends BusinessValidator>>

&#x20;       validatorRegistry = Map.of(

&#x20;           "VALIDATOR\_CHECK1", ValidatorCheck1.class,

&#x20;           "VALIDATOR\_CHECK2", ValidatorCheck2.class

&#x20;       );

The map connects each configured name to its Java class.



**Step 5: executes the configured validation rules one by one, so the payment request is checked before it reaches the payment provider.**

Name — Which validator should run?

Class — Which Java class matches that name?

Object — Get the Spring bean.

Method — Call validate().







**Final execution flow**

Incoming payment request



Security validation

&#x20;    HMAC-SHA-256

&#x20;       || 

Field validation

&#x20;   Spring Validation

&#x20;       ||

Business validation

&#x20;   Execute configured rules one by one

&#x20;       ||

All rules pass → Call Stripe provider

Any rule fails → Stop and return the first error.
