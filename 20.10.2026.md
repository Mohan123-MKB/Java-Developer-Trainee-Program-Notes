Day 8 of My Java Backend Developer Journey = Package Standards & REST API Best Practices

Today, I learned about proper package organization in Spring Boot and best practices for designing clean, consistent, and maintainable REST APIs.

1. Package Standards:

I learned how to organize application code into packages based on their responsibilities: For easier to understand, maintain, and test.

controller – Receives HTTP requests and returns responses.

service – Contains business logic and processes requests.

repository – Communicates with the database.

entity – Represents database tables and their data.

DTO – Transfers data between the client and application.

config – Contains application configuration, such as security settings.

constant – Stores fixed values used throughout the application.

exception – Handles application errors and exceptions.

util – Contains reusable helper methods.

http – Organizes HTTP communication-related components, when needed.

POJO – Contains ordinary Java objects used to hold data.

2. REST API Best Practices:

1. Resource-Based URLs: Use meaningful URLs such as /v1/employees and /v1/payments.

2. Appropriate HTTP Methods: Use GET, POST, PUT, PATCH, and DELETE according to the operation.

3. API Versioning: Include version numbers such as /v1 to manage API changes.

4. Proper HTTP Status Codes: Use appropriate codes such as 200 OK, 201 Created, 204 No Content, and 404 Not Found.

5. Separation of Responsibilities: Keep controller logic separate from business logic by using the service layer.

6. DTO Usage: Use Data Transfer Objects (DTOs) for request and response data instead of directly exposing database entities.

7. Consistent Naming and Error Handling: Follow consistent naming conventions and return meaningful error responses.

Key Takeaway:

Proper package organization and REST API best practices help build clean, scalable, maintainable, and easy-to-test backend applications.

REST and Resource:
Rest revolves around the concept of resources, for building any rest APIs we need to work with resources only.
A resource is anything that can be uniquely identified and accessed or manipulated over the web using a URL. This URL contains (http methods and path endpoints).
HTTP methods - A specify the type of operation a client wants to perform on a server resources. (CRUD operations)
e.g. GET /v1/employees/1
	 GET → HTTP method (operation)
	 /v1/employees/1 → Endpoint (identifies the resource)
	 1 → Employee ID
-------------------------------------------------------------------------------------------
URL:
A URL identifies the resource or endpoint the client wants to access.
URL consists of http methods and path endpoint, when URL http requests comes from browser then mapping will happen on of the controller method based on http methods and proper endpoints.

-------------------------------------------------------------------------------------------
REST principles:
1. Client–Server: 
Client sends requests; server processes them and returns responses.
2. Stateless: 
Every request contains the information needed to process it. The server doesn't store client session state between requests.
3. Cacheable: 
Responses can be stored and reused when caching is allowed, improving performance.
4. Uniform Interface: 
Use a consistent way to access resources with URIs and HTTP methods like GET, POST, PUT, and DELETE.
5. Layered System: 
Requests can pass through intermediaries like API gateways, proxies, or load balancers.
6. Code on Demand (Optional): 
The server can send executable code, such as JavaScript, to the client.
-------------------------------------------------------------------------------------------
REST API design guidelines or best practices:

1. Resource-Based Design:
A resource is anything that an API allows clients to access and manage, such as students, users, products, or orders. Example: /users/101 identifies a user with ID 101.

2. Use HTTP Methods Correctly: [GET, POST, PUT, PATCH, DELETE].

3. Use Meaningful URLs:
Use nouns instead of verbs in endpoint URLs. The HTTP method defines the operation.
	* Good: /users, /products, /orders/101
	* Bad: /get Users, /create Product, /delete Order

4. Use JSON for Data Exchange: REST APIs commonly use JSON to send and receive data.

5. Use Query Parameters: Support filtering, sorting, and pagination.
	Filtering: /products? Category=electronics
	Sorting: /products? Sort=price, asc
	Pagination: /products? Page=2&size=10

6. Version Your API: Versioning helps introduce changes without unexpectedly breaking existing clients. Example: GET /v1/users or Manage API changes safely.

7. Use Appropriate HTTP Status Codes:
Status			  Meaning
200 OK		  	 Request successful
201 Created		 Resource created
204 No Content		 Successful request with no response body
400 Bad Request		 Invalid request
401 Unauthorized	 Authentication is missing or invalid
403 Forbidden		 Access is not permitted
404 Not Found		 Resource not found
500 Internal Server Error Unexpected server error

8. Handle Errors Gracefully: Return a suitable HTTP status code and a meaningful error message. e.g.
{
  "status": 404,
  "message": "User not found",
  "details": "No user exists with ID 101"
}
-------------------------------------------------------------------------------------------
Exposing Functionality Without a Clear Resource:

Prefer resource-oriented REST endpoints when practical. When an action cannot be naturally represented as standard CRUD, an operation-oriented endpoint can still be a reasonable design choice. Example: Payment Processing => A payment is a resource, and processing it is an operation.

1. Create a payment
POST /v1/payments

2. Confirm the payment
POST /v1/payments/{payment Id}/confirm

Key takeaway: Use /payments to create a payment and /confirm to perform a specific operation on it.
