**2.1 Need of Payment Integration System:**



overall summary (12 points)

* In real world we have merchant system that offer products or services through online.



* End customer buys this product/service through online.



* Merchant should offer as maximum payment options as possible for end customer.



* Each payment option might be a 3rd party technical company and needs to be integrated into system if we want to use them.



* Its not practical to integrate with so many individual systems and lot of challenges are there like time, security, license.



* Merchant has option to integrate with some intermediate systems like direct card processors, payment gateways, aggregators.



* Even after integrating with these intermediate systems, there is still some risk, or additional features which needs to be built on merchant system.

&#x20;

* Using a PSP we will get lot of additional features along with core payment processing and PSPs will be integrate lot of payment options behind the screen.



* As a merchant good to integrate with PSP.



* There are multiple PSPs in the market(Stripe, PayPal, Trustily, Square, etc..) and we use fully depends on user base around the world.



* Business team will decide which one is most suitable for integrating into the merchant system.



* Business team shares the integration document(to know the technical complexity and estimation/resources for building such applications) to the tech team(now tech team gets involved).

**2.2 why merchant system is arranged in 2 separate system(merchant functionality and payment integration system):(10 points)**



* Merchant system has 2 responsibilities(core business functionality and payment functionality).



* Instead of building payment logic inside every merchant service, create a separate Payment Integration System.



* All payment-related capabilities are centralized in one system are called payment integration system.(payment processing, stripe integration, refunds, webhooks, payment status tracking)



* Dedicate payment experts can manage and enhance this system independently.



* Payment industry changes frequently so all changes are handled only inside the payment integration system.



* Future PSP(Stripe, PayPal, Razor Pay) can be added easily in out merchant application



* Merchant systems integrate only PIS through standard APIs.



* Minimal changes are required in merchant applications when payment-related changes occur.



* Benefits: Separation of concerns, Reusability, Easier maintenance, Scalability, Reduced complexity for merchant teams.



* Flow: "End customer -> Merchant -> Payment Integration System (Stripe Integration Business Logic) -> Stripe PSP"



Terminology:

Payment Method: **Alternate Payment Method**, card

Payment Service Provider(PSP): PayPal, **Stripe**, Razor Pay, Trustily, Square, etc...

Payment Type: SALE(one time payment)

**3. Stripe Checkout lifecycle:**



* When customers are ready to complete their purchase , our application creates a new Checkout Session.



* The Checkout Session provides a URL that redirects customers to a Stripe-hosted payment page.



* Customers enter their payment details on the payment page and complete the transaction.



* After the transaction, a webhook fulfills the order using the checkout.session.completed event.

**4. Complete end to end workflow of stripe payment integration system:**



We have multiple systems interacting to make payment possible with stripe(Merchant FE and BE, Payment Integration System \[validation-service, stripe-provider],external Stripe PSP)



1. when end-customer is on the cart page/checkout page, there will be option to make payment.



2\. when customer clicks make payment, Merchant FE calls merchant BE(don't directly call  PIS)



3-4. Merchant BE, validates the FE request and validates the card amount, product, checks then makes the call to payment integration system.



5\. payment-validation-service receives this API call, then uses spring security with HMAC to validate the merchant authentication, and then runs field and business validation to ensure request is valid and can be processed further.



6-7. Further it calls payment-processing-service(responsible for core payment processing), which will call stripe-provide-service.



**Note: For this 2 months we are building payment-validation-service and stripe-provide-service and processing service we can do in future.**



8-9-10-11-12-13. stripe-provider-service is responsible to all stripe interaction, so it will make create session Stripe API call => gets the response with URL => returns it back to validation-service => merchant backend => merchant FE is redirected to Stripe Hosted  Payment Page. \[Stripe checkouts workflow]



14-15. End-customer completes payment in stripe hosted page. Stripe process it and determines final success/failure.



16.1 The stripe hosted page is redirected back to merchant page.



16.2 Stripe invokes our stripe-provider API with checkout.sessions.completed event (JSON body)



17-18-19. Stripe-provider will process this event and inform payment-processing-service. Which further can make Async call to merchant system to inform the final status.(you can use a message broker like Kafka.)



20\. Merchant system connects to message brokers as a listener for receiving and processing the final data.



21\. Merchant system will further drive the logic to issue the product/service to the end customer.
