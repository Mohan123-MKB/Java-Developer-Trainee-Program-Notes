1. #### Componentization via service =



Each service have own business logic(spring boot application) and each service should have its own port, have its own process id, have its own memory, have its own database, coded independently, deployed independently, scale independently, write code in different language.

The goal is to build services that can evolve independently without impacting other parts of the system.

#### 2\. Organized around Business capabilities = Many features are there



**scenario 1** : put related functionalities together =>

\-put related functionality together in one microservice.

\-You can consider a thought, if f1 is affected, are you ok that even f2 gets affected(due to build/deployment)

&#x20;    -if you can ok, both features to be affected even for failure of f1,that mean they are really closely related, and can be in same microservice.

&#x20;    -if you are not ok, then think of splitting it into another microservice.



&#x09;				Ask:

"If Feature A changes or fails, is it acceptable for Feature B to be impacted too?"

If YES → Same microservice.

If NO → Separate microservices. This is called finding the bounded context.



&#x20;                                     Example:

Product Service

&#x20;├─ Add Product

&#x20;├─ Update Product

&#x20;└─ Delete Product



Payment Service

&#x20;├─ Process Payment

&#x20;└─ Refund Payment



**scenario 2** : Team arrangement => Whatever team members/skillset needed to work on that microservice should be working together as one team. cross team dependency will not be there.



**scenario 3** : size of microservice || no small(due to avoid maintenance work) and no large(due to avoid failure, hard to maintenance- testing- debugging)  => Have only that size of MS which can be managed by around 6-8 people. If you have more feature code to add in the same MS, then better to split into another one.(hire new engineer)

#### 3\. Smart Endpoints and Dumb Pipes(over network) =



* Network call happen here: MS1 wants to communicate with MS2 to get info from other service.\[Expose MS2 code as endpoints then MS1 call this endpoints to make request to get response from MS2 service.]
* Multiple ways of communication between 2 services:

&#x09;-If need immediate response = use sync(Rest APIs)

&#x09;-If no need immediate response = use Async 1(Messaging System - Event driven architecture; highly scalable system will be maintained; continuous parallel execution)

&#x09;-Non-blocking system with Rest APIs = use Async 2(Reactive API call - web flux and web client)

* In a microservices architecture, one microservice (MS1) may need to communicate with another microservice (MS2) over the network.
* This principle says:

&#x09;-Keep all business logic inside the microservices (Smart Endpoints).

&#x09;-Keep the communication channel simple and lightweight (Dumb Pipes).

&#x09;-The network should only transfer data and should not contain business logic.

* Any microservice can be developed in any programming there are 2 common ways of communication happen SYNC and ASYNC:

&#x20;       -**Sync communication**: You call, you wait for response, once you get response then resume further execution, you need the destination service to be up and running to make this call, when you need immediate response/processing then sync communication  do it, spring provides feign client(spring web) for make sync calls.

&#x20;       -**Async communication:** Improves scalability and throughput, Doing parallel process you start a task then move to another task in parallel without waiting on previous response. For making Async we can have in 2 styles ->

&#x20;            \* Using Messaging system(message broker) : you have some message broker software in middle man like Kafka, ActiveMQ, RabbitMQ;

&#x20;                                                       sender sends message(data) to the message broker and sender continues its executing without really check if consumer is there, or whether the request is processed.. sender don't wait for consumer response.. it just moved on next execution;

&#x20;                                                       the message will be kept in message broker and when receiver is available, it consumes and processes. you can build high scalable systems using Async style;

&#x20;                                                       use Async wherever its  ok to have some delay in processing (payment after successful confirmation message via notification like that)then you can prefer this approach.



&#x20;            \* Using Reactive(web flux module and web client library) : The destination should be up and running;

&#x20;                                                                       there is no broker involved sender directly calls destination and without waiting for response and moves to the next execution in non-blocking style;

&#x20;                                                                       when destination returns response then sender can process using callbacks(handle async results);

&#x20;                                                                       Using web flux(web client) we can achieve this style of communication.

#### 4\. Design for failure: Implement Error Handling



* Microservices are distributed systems.
* Failures are not exceptions, they are expected.
* Potential issues include:

&#x09;Network failures

&#x09;Timeouts

&#x09;Packet loss

&#x09;Resource exhaustion (CPU, Memory)

&#x09;Thread starvation

&#x09;Unexpected exceptions

* The goal is to proactively design systems that can withstand failures..



&#x20;   **Technical solutions:**



1\. Circuit Breaker:

When a downstream service is unhealthy:

&#x20;	Stop sending requests temporarily

&#x09;Fail fast

&#x09;Retry after some time

Benefits:

✅ Prevents cascading failures

✅ Preserves resources

✅ Improves system resilience



2\. Error handling system:

&#x09;Return meaningful error responses

&#x09;Handle expected exceptions gracefully

&#x09;Monitor application health

Useful tools/practices:

&#x09;Spring Boot Actuator

&#x09;Centralized Logging

&#x09;Distributed Tracing

&#x09;Monitoring \& Alerting
